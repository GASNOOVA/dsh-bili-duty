## 2. 目标形态

> 一个「值守型」插件：平时安静，主播开播就进房陪伴，顺手把今天该做的亲密度任务做完；设置页能看到 5 个主播各自的任务完成情况，能临时加一条开播计划。

## 3. 每日任务模型（每主播 × 每天）

北京时间自然日（沿用代码 `dayKey()` 的 +8h 口径）重置。状态结构（`state.json`）：

```jsonc
{
  "day": "2026-11-10",
  "rooms": {
    "12345": {                      // realRoomId
      "mid": "67890",
      "name": "主播A",
      "watchedSec": 3600,           // 当日累计驻留秒数（观看任务依据）
      "watchReported": 0,           // 已上报/可验证的观看秒数（探针后填充）
      "danmakuDone": true,          // 当日是否已成功发过 ≥1 条
      "danmakuCount": 3,            // 当日发送总数（任务+AI+模板）
      "likeDone": true,             // 当日是否已成功点赞过
      "likeClicks": 900,            // 当日累计点击数
      "lastLikeAt": 1760000000000,  // 上次点赞轮次时间（用于 10 分钟节流）
      "giftDone": false,            // 当日打赏是否完成/跳过
      "giftState": "skipped",       // done | skipped_balance | disabled | failed
      "lastDanmakuAt": 1760000000000,
      "lastGiftAt": 0,
      "errors": []                  // 最近 3 条错误（脱敏）
    }
  },
  "streamers": { "mid-xxx": { "lastLiveAt": 0, "lastEnterAt": 0 } }
}
```

任务判定：
- **发送弹幕**：当日该房 `danmakuDone=true` 即完成（B 站任务通常只要 1 条；以实测为准）。
- **点赞**：当日该房 `likeClicks>0` 即完成最低要求；300 次/10 分钟是「陪伴期间持续做」的行为，不设日上限（按你的要求）。
- **观看**：`watchedSec` 累计；具体门槛未确认，设计上不主动离开正在播的主看房，直到下播（天然覆盖要求的分钟数）。
- **打赏**：当日该房 `giftDone=true`（成功或明确跳过）即视为当日了结，不重试。

## 4. 调度设计

两个调度源并行，共享同一个「当前目标房间」：

### 4.1 自动模式
- 每 `autoCheckMs = 15 分钟` 检查一次 5 个主播的开播状态（复用 `getRoomByUid`/`getRoomInfo`）。
- 仅在**北京时间 08:00–24:00** 内执行进入/值守动作；工作时间外不进入新房间（已在房间时是否退出？**建议保留到当前场结束**，不主动退）。
- 选主看房规则（默认规则，可按配置调整优先级）：按列表顺序（即优先级）取第一个在播的主播；当前主看房仍在播就不换。
- 进房后：连弹幕、拉低清流、按任务表执行点赞/弹幕/打赏；主播下播 → 回到选房逻辑。

### 4.2 手动计划
- 数据：`plans[] { id, mid, name, at (计划开播时间, 本地/北京时间), createdAt, fired, result }`，一次性（触发后标记完成，不进历史）。
- 触发：`at - 10 分钟` 进房（即使未开播，先挂着等 —— 你的明确要求）。
- 工作时间（已确认）：手动计划**不受** 08:00–24:00 限制，按计划时间执行；自动模式仍受工作时间限制。
- 等待：到 `at` 后仍未开播 → 最多再等 10 分钟（共 20 分钟），超时标记 `missed`，退出等待。
- 提前进房后如果主播迟迟不开播：保持房间页面在线（弹幕连接），不执行任务（房间没开播时点赞/弹幕无意义且有风险）。
- 多条计划同时到期：都进不了同一时刻 —— 按「计划时间早 → 列表顺序」取第一条作为主看房，其余计划转为「任务房候补」，满足 §4.3 的补任务条件时再切换。

### 4.3 多主播同时开播：主看房 + 任务房切换（核心规则）

1. **主看房（陪伴）**：手动计划目标优先；其次自动模式按列表顺序第一个在播；已在播就不换。
2. **补任务**：每 `taskSweepMs = 5 分钟` 检查其余在播主播的房间，若存在「今日弹幕未完成」或「今日点赞未完成」或「今日打赏未做」→ 切过去。
3. **任务房动作**：进房后依次：打赏（若启用且未做）→ 确认今日弹幕任务（问候已发则跳过；当天问候失败则补 1 条问候模板）→ 点赞一轮 300 次；全部完成即切回主看房。若某任务失败（风控/等级限制），记录并跳过，不原地硬重试。
4. **主看房切换**：主看房下播 → 从剩余在播主播中按优先级选新主看；都下播 → 等待下一轮检查。
5. **任务房驻留上限**：单次任务访问最长 `taskVisitMaxMs = 10 分钟`，超时强制回主看房（避免陪着任务房忘了主看）。
6. **冲突处理**：切换过程中主看房下播 → 直接按新主看逻辑走，不回头。

> 这套规则实现了你要的「先切到没做弹幕与点赞的直播间做完任务，再切回主看房」。

## 5. 任务执行器

### 5.1 点赞（新增，现有代码没有）

- 行为：每房每 10 分钟一轮，一轮共 300 次。**P0 实测：房间下发策略为 `like_info_v3.report_click_limit=15`、`report_time_min=5s`** —— 所以 300 次必须拆成 **20 批 × 15 次**，批间隔 ≥5 秒 + 随机抖动（一轮约 2–2.5 分钟），轮与轮间隔 10 分钟（含抖动）。每批请求带 `click_time` = 批内次数（≤15）。
- 接口（P0 已确认）：`POST https://api.live.bilibili.com/xlive/app-ucenter/v1/like_info_v3/like/likeReportV3`，form：`room_id / anchor_id / uid / click_time / csrf / csrf_token / visit_id`；进房先 `POST /xlive/web-room/v1/index/roomEntryAction`（可选）；策略读 `GET /xlive/web-room/v1/index/getInfoByRoom?room_id=` 的 `like_info_v3`。
- 返回码：区分成功 / 未登录 / csrf / 频率限制 / 需要验证 / 未知。**失败即停本轮**，记录 code 与时间；当日失败 2 次后不再尝试该房点赞（避免激怒风控）。
- 风控降级（已确认）：若实测 300 次连点触发风险码/验证码 → 先降级为**分批 100×3 + 加大随机间隔**（总数仍 300）；仍不行再减少轮次或停用点赞，并把降级记录写进日志与状态。
- 亲密度任务完成：当日第一次成功点击即 `likeDone=true`；300 次是行为要求，不设日上限。
- 浏览器/账号状态：若接口返回需要验证码/风险校验 → 全局暂停互动任务并提示（§8）。

### 5.2 弹幕（复用 `sendDanmaku`）

两条通道，共用限速：

**A. 模板弹幕**（已锁定：**仅进房问候**，默认发 10 条，数量可配 1–20；下播告别已移除）：
1. 进房问候：**每房每天只做一次**（当天首次进入该房时），从「问候模板库」随机不重复取 `templateGreetingCount` 条（默认 10，范围 1–20），按 `templateSpacingMs`（默认 30 秒，范围 10–120 秒）依次发送；第一条同时保证「发送弹幕」每日任务完成（默认开）。当天再次进入同一房间不重复问候。
2. **下播告别已移除**：主播下播时不再发送任何模板弹幕（下播瞬间弹幕通道可能已关闭，且属于无意义风险动作）；下播后插件只做「离开房间 + 更新任务状态」。
3. 模板库：一组可编辑列表（默认内置 10 条占位，如「来了」「晚上好」…）；库不足发送条数时循环使用，设置页提示补足。模板内容与最终条数由你后续提交/配置，代码不写死。
4. 发送计数：模板弹幕同样计入每房每日总上限与全局限速；失败（风控/等级限制/直播间关闭）只记日志与状态，不硬重试。
5. 若某房当天问候全部失败、且 AI 弹幕关闭，则「发送弹幕」任务会漏做：状态表标红，并在调试区提供「手动补发一条问候」按钮（不设独立的任务保底通道，避免多一条自动发送路径）。

**B. AI 智能弹幕**（开关默认开；高频档，参数可在设置页调）：
- 上下文：房间标题、主播名、最近 30 条弹幕（去重/截断）、当前时间；**不启用 ASR/画面**（保持轻量；若以后要「听到内容」，再评估）。
- prompt 约束：≤20 字、像观众随口搭腔、不 @ 人、不引战、不刷屏、不重复历史发言、不提 AI/机器人。
- 频率（已锁定）：进房后延迟 `aiDanmakuMs`（默认 **300 秒**，范围 **30–600 秒**）发送第一条，之后每 `aiDanmakuMs` 最多 1 条；每房每日上限 `aiDanmakuDailyMax`（默认 **100 条**，范围 **10–300 条**）。
- 去重：与最近 20 条已发弹幕做相似度检查，重复则重新生成一次，仍重复则放弃本次。
- 失败降级：模型不可用/超时 → 静默跳过（不阻塞）；问候模板仍会完成每日任务。
- ⚠️ 风险提示：默认 300 秒/条、100 条/日属于高频互动，与「风控接受度最低」有张力；首周建议观察风控情况，必要时把 `aiDanmakuMs` 调大、`aiDanmakuDailyMax` 调小（设置页可改，不用改代码）。

**C. 限速与总上限**：
- 全局硬下限 `danmakuCooldownMs`（默认 **3 秒**，范围 1–60 秒）：任意两条弹幕之间的绝对最小间隔，只作兜底；实际间隔由各通道参数决定（问候 30 秒、AI 300 秒）。
- 每房每日总上限 `danmakuDailyMax`（默认 **150 条**，范围 20–600 条）：问候 + AI 之和的兜底；默认参数下一天最多 10 + 100 = **110 条/房**；若通道参数之和超过总上限，按总上限截断（优先保留问候首条，其余从 AI 里让位）。
- 风控错误码 → 暂停该房发弹幕 10 分钟并提示；同一房当天弹幕失败 3 次后停用该房弹幕任务（状态保留为未完成）。

### 5.3 观看直播（拉低清流 + 心跳）

- 目标：让平台把「观看直播」任务的分钟数计入。分三层验证：
  1. **基础层（必做）**：进房即连 `DanmakuClient`（已有能力），房间在线状态可见。
  2. **拉流层**：复用现有 FLV 拉流能力，拉 `qn=80`（或最低档）只读取丢弃（不落盘、不解码），断流 3–5 秒重连；记录拉流时长。
  3. **上报层（探针确认）**：如果平台靠播放器心跳/上报接口统计，按探针结果补调（候选：播放器心跳 / 观看上报接口）。
- 降级：拉流层不稳定 → 只保留基础层 + 上报层；都不可行 → 按你的要求「放弃观看任务」，状态表标注 `watchUnsupported`。
- 资源：同一时刻最多拉 1 路（主看房），任务房不拉流。**P0 实测**：拉流链路正常，测试房间只提供 qn=250（请求 qn=150 会回落到 250），约 **300 KB/s（≈18 MB/分钟）**。
- **观看时长口径（用户确认 + P0 实测）**：B站 粉丝团亲密度按观看时长增长，**每 15 分钟结算一次**；只拉流 5 分钟亲密度没有任何变化（today_feed 保持 1）。因此「观看任务」必须保持**完整在场**（进房接口 + 弹幕长连接心跳 + 拉流）连续 ≥15 分钟才会入账。插件实现为「进主看房后持续拉流 + 弹幕心跳」，只在主看房累计；补任务的房间不做观看。

### 5.4 打赏（可选，探针决定是否保留；已确认探针可真实送 1 次验证）

- 规则（你已硬性限定）：
  - 每主播每天最多 1 次；
  - 礼物 = 「粉丝团灯牌」，价格必须 **≤ 1 电池**（以礼物配置接口返回的价格为准；若该账户内该礼物价格不是 1 电池，则先不实现，等你确认）；
  - 使用账号电池余额；**余额不足直接跳过**，不充值、不借贷、不换付费货币；
  - 全局每日最多 5 次（= 主播数上限）；失败不重试；接口需要验证则跳过并提示。
- 流程：查礼物配置（gift id/价格）→ 查余额 → 校验价格与余额 → 发送 1 个 → 记录结果与时间。
- **P0 只读实测**：`GET /xlive/web-room/v1/giftPanel/giftConfig?room_id=` 可读到 1004 个礼物，其中「粉丝团灯牌」有多条记录；按 `price=100 / coin_type=gold`（=1 电池，依据页面文案「加入粉丝团（1电池）」）取对应 `gift_id`，真实礼物 id 还需按房间礼物列表/场景确认唯一值。钱包 `GET /xlive/revenue/v1/wallet/myWallet` → `gold=9400`（≈94 电池）、`silver=0`。粉丝牌 `GET /xlive/app-ucenter/v1/fansMedal/user_medal_info?uid=&up_uid=` 可判断是否已入团——测试主播**未入团**，所以真实送礼测试暂缓（避免顺带入团），等目标主播开播后用已入团的房间测。
- 若探针证明无法用 HTTP 接口完成 → 按 A1 从产品中移除该功能（代码不保留死开关，页面也不显示）。
- **红线**：任何情况下不发送价格 > 1 电池的礼物；不因重试产生第二次扣费。

## 8. 风控与安全设计（默认最保守）

1. **限速与抖动**：所有写操作（点赞/弹幕/送礼）加随机抖动；弹幕全局冷却 30s；点赞并发 ≤2、轮间隔 10 分钟带抖动。
2. **失败即停**：任何写操作失败不自动重试；同一动作当日失败 2 次后停用该动作（记录状态），避免触发风控。
3. **验证码/风险识别**：接口返回需要验证（如 `-352`/`-412`/验证码相关码）→ 全局暂停互动任务并提示「请手动登录/验证后重试」；不做绕过。
4. **每日上限**：弹幕每房 ≤ `danmakuDailyMax`（默认 150 条；默认参数下实际最多约 110 条 = 问候 10 + AI 100）；点赞无日上限（按需求）但全局请求速率封顶；打赏每房 ≤1 次、全局 ≤5 次/日。
5. **预算硬限制**：打赏礼物价格 ≤1 电池，且只允许单价=1 的「粉丝团灯牌」；余额不足直接跳过；不自动充值、不兑换。
6. **工作时间**：自动模式 08:00–24:00；**手动计划不受限制**（已锁定）。
7. **安全边界**：只绑本机；`/api/bili-live/*` 仍无鉴权 → 沿用「只给本机用」；新增探针接口只返回脱敏原始响应（不含 cookie/凭证）。
8. **合规提示**：自动化点赞/发弹幕/送礼属于对平台的非官方自动化操作，可能违反 B 站用户协议并导致风控、限流或封号；本插件只在你自己的账号上、按你的指令执行，风险自担。设置页需要放一段说明并要求勾选确认后才启用互动任务。

## 9. 技术探针（决定打赏/观看能不能做）

探针是设置页里的手动按钮（只发 1 次请求、不做自动流程），或独立 `node` 脚本（不用装插件即可跑）。每个探针记录：请求、HTTP 状态、返回 code/message、耗时、脱敏 raw。

| 探针 | 目的 | 通过标准 | P0 结果（2026-11-09） |
| --- | --- | --- | --- |
| A. 点赞 | 确认点赞接口可用 + 返回码语义 | 返回 code=0（或已知成功码），且任务面板计数/亲密度有变化 | ✅ **通过**：likeReportV3 code=0；房间策略 15 次/批、最小间隔 5s |
| B. 礼物配置 | 找到「粉丝团灯牌」gift id 与价格单位 | 能读出 gift id、name、price；price 对应 1 电池（与你的描述一致） | ✅ **通过**：giftConfig 可读；找到 1 电池档（price=100 gold）的「粉丝团灯牌」 |
| C. 余额 | 读账号电池余额 | 能读到数值；不足以支付时能看到 | ✅ **通过**：myWallet → gold=9400（≈94 电池）、silver=0 |
| D. 送礼（会真实扣 1 电池） | 确认送礼接口可用 | 返回成功且余额 -1；需要单独确认这次 1 电池的测试 | ✅ **通过**：`sendGoldMultiUser` code=0；gift_id=31164「粉丝团灯牌」100 gold；钱包 9400→9300；粉丝牌 `is_gain=true` 新增「蜂群们」（intimacy=1, today_feed=1, is_lighted=1） |
| E. 观看上报 | 确认拉流/心跳是否计入观看任务 | 连续完整在场 ≥15 分钟后亲密度/today_feed 增长（用户确认：15 分钟结算一次） | ✅ **通过**：16 分钟完整在场（进房 + 弹幕 WS 心跳 + 拉流 960s）后粉丝牌 intimacy 1→3、today_feed 1→6、等级 1→2；反例：只拉流 5 分钟无变化 |

探针结果决定：A/D 失败 → 移除打赏；E 失败 → 降级或放弃观看任务；A 失败 → 点赞任务移除（那这版就只剩弹幕 + 观看）。
